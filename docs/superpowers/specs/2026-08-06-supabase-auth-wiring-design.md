# Supabase Auth Wiring — Design Spec

**Status:** Approved by user 2026-08-06, pending final spec review before implementation plan.

## Goal

Wire real Supabase Auth into `apps/wellness` (email+password), replacing the decorative `family-login.html`/`login.dc.html` mockups, and extend the schema so one login account can be linked to multiple members (patients) and one member can be linked to multiple accounts (patient + family).

## Context

- Hosted Supabase project "Care Bridge App" (ref `bbthbboakoicoyiuclll`) is linked, 9 migrations pushed, `@carebridge/db-types` generated from it.
- Current schema: `profiles.id` references `auth.users.id` (1:1, auto-created via `handle_new_auth_user` trigger, role defaults to `member`). `members.user_id` is a single nullable FK to `auth.users.id` — this is the piece being replaced.
- V1_SCOPE.md: members are created by coordinators in Admin, not self-service. Admin gets no invite-code UI in this phase — invite codes are generated by the developer via SQL/script for now.
- Audience includes NRI family members abroad managing a parent's care in Kerala — driving the "one account, multiple members" and "patient + family both get logins" requirements.

## Decisions (from brainstorming)

1. **Auth method:** email + password (not phone/OTP — avoids SMS provider setup and cost for V1).
2. **Account↔member relationship:** many-to-many. One login can be linked to multiple members; one member can have multiple linked logins (the patient's own account and one or more family members' accounts).
3. **Who holds accounts:** both patients and family members can have their own login, all linked accounts to a member see that member's data equally (no tiered permissions in V1).
4. **Linking mechanism:** invite codes. Coordinator generates a code tied to a member (SQL/script for now); the account holder redeems it once, self-serve, inside the app.
5. **Email verification:** skipped for V1. The invite-code redemption is the real trust gate — a plain unverified email is not the security boundary here.

## Schema Changes

New migration on top of the 9 already pushed. All new SQL, no edits to old migration files (already applied to hosted).

**`member_links`** — replaces `members.user_id` as the source of truth for member access:
```sql
create table public.member_links (
  id uuid primary key default gen_random_uuid(),
  member_id uuid not null references public.members(id) on delete cascade,
  user_id uuid not null references auth.users(id) on delete cascade,
  relationship_label text not null default 'Family member', -- e.g. 'Self', 'Son', 'Daughter', 'Spouse'
  is_self boolean not null default false,
  created_at timestamptz not null default now(),
  unique (member_id, user_id)
);
create index member_links_user_id_idx on public.member_links(user_id);
create index member_links_member_id_idx on public.member_links(member_id);
```

**`member_invites`** — one-time codes, redeemed by the account holder:
```sql
create table public.member_invites (
  id uuid primary key default gen_random_uuid(),
  code text not null unique, -- short human-typeable code, e.g. 8 chars uppercase alnum
  member_id uuid not null references public.members(id) on delete cascade,
  relationship_label text not null default 'Family member',
  is_self boolean not null default false,
  created_by uuid references public.profiles(id),
  expires_at timestamptz not null default (now() + interval '14 days'),
  used_at timestamptz,
  used_by_user_id uuid references auth.users(id),
  created_at timestamptz not null default now()
);
create index member_invites_member_id_idx on public.member_invites(member_id);
```
RLS on `member_invites`: no client-facing select/insert/update/delete policy at all — the table is reachable only through the `redeem_invite_code` RPC below (security definer) and coordinator-run SQL. This keeps invite codes unguessable-by-query even for authenticated users.

**`redeem_invite_code` RPC:**
```sql
create or replace function public.redeem_invite_code(p_code text)
returns uuid -- returns member_id on success
language plpgsql security definer set search_path = public as $$
declare
  v_invite public.member_invites;
begin
  select * into v_invite from public.member_invites
    where code = p_code and used_at is null and expires_at > now()
    for update;

  if not found then
    raise exception 'invalid_or_expired_code';
  end if;

  insert into public.member_links (member_id, user_id, relationship_label, is_self)
    values (v_invite.member_id, auth.uid(), v_invite.relationship_label, v_invite.is_self)
    on conflict (member_id, user_id) do nothing;

  update public.member_invites
    set used_at = now(), used_by_user_id = auth.uid()
    where id = v_invite.id;

  return v_invite.member_id;
end;
$$;

grant execute on function public.redeem_invite_code(text) to authenticated;
```

**RLS helper functions updated** (`member_owns`, `can_access_member` in `20260805091858_members_care_team.sql`) — new migration replaces their bodies to check `member_links` instead of `members.user_id`:
```sql
create or replace function public.member_owns(p_member_id uuid)
returns boolean language sql stable security definer set search_path = public as $$
  select exists (
    select 1 from public.member_links ml where ml.member_id = p_member_id and ml.user_id = auth.uid()
  );
$$;
```
`is_assigned_coordinator` and `can_access_member` (which composes `member_owns` + `is_assigned_coordinator`) are unchanged in signature — no other migration file needs edits since everything downstream reads through `can_access_member`/`member_owns`.

**`members.user_id` column and its index are dropped** — no longer the access-control source of truth. The `"member updates own member record"` policy in `20260805091858_members_care_team.sql`, which reads `using (user_id = auth.uid())`, is replaced with a `member_owns(id)`-based policy in the new migration.

**`member_links` RLS:**
```sql
alter table public.member_links enable row level security;
create policy "user reads own member links"
  on public.member_links for select using (user_id = auth.uid());
create policy "coordinators read all member links"
  on public.member_links for select using (public.is_coordinator());
```
No client-facing insert/update/delete policy — rows are created only via `redeem_invite_code` (security definer, bypasses RLS) or coordinator SQL.

## Auth Flow

1. **Signup** (`apps/wellness`, new `/signup` route): email + password form → `supabase.auth.signUp({ email, password })`. No email confirmation (Supabase project setting: disable "Confirm email"). The existing `handle_new_auth_user` trigger creates the `profiles` row automatically — no app-side insert needed.
2. **Login** (`/login`, replaces the decorative mockup): email + password form → `supabase.auth.signInWithPassword(...)`.
3. **Post-auth routing** (in `AuthProvider`, see below): session exists but `member_links` for this user is empty → force `/link-member` (invite-code entry). Session exists and ≥1 link → `/` (Home), with the active member defaulting to the `is_self` link if present, else the first link by `created_at`.
4. **Link another member** (reachable from Settings/More once already past onboarding): same `/link-member` screen, calls the same `redeem_invite_code` RPC, then returns to Home.
5. **Member switcher**: rendered in the app header only when the current user's `member_links` count > 1. Selecting a member updates `AuthProvider`'s `selectedMemberId` (in-memory + persisted to `@capacitor/preferences` so the choice survives app restarts).

## Session Persistence

`@supabase/supabase-js`'s `createClient` is configured with a custom `storage` adapter backed by `@capacitor/preferences` instead of the default `localStorage`. Reason: WKWebView (iOS) can evict `localStorage` under memory pressure or after prolonged inactivity; `@capacitor/preferences` persists to native `UserDefaults`/`SharedPreferences`, surviving app kills. New dependency: `@capacitor/preferences` (added to `apps/wellness/package.json` — same vendor as the already-present `@capacitor/core`/`ios`/`android`).

The storage adapter implements the 3-method interface `supabase-js` expects (`getItem`/`setItem`/`removeItem`), each wrapping the corresponding `Preferences` call.

## App Structure

- `apps/wellness/src/lib/supabase.ts` — creates and exports the configured Supabase client singleton.
- `apps/wellness/src/lib/storage-adapter.ts` — the `@capacitor/preferences`-backed storage adapter.
- `apps/wellness/src/auth/AuthProvider.tsx` — React context. State: `session`, `memberLinks` (array of `{memberId, relationshipLabel, isSelf}`), `selectedMemberId`, `loading`. Subscribes to `supabase.auth.onAuthStateChange`; refetches `member_links` on session change.
- `apps/wellness/src/auth/useAuth.ts` — hook exposing the context.
- `apps/wellness/src/auth/RequireAuth.tsx` — route guard component implementing the routing rules in step 3 above.
- `apps/wellness/src/pages/Login.tsx`, `Signup.tsx`, `LinkMember.tsx` — the three auth-flow screens, styled per the existing `login.dc.html` mockup (mobile number field swapped for email) via `@carebridge/design-system`'s existing CSS classes (`.login`, `.login__art`, `.login__form`, `.field`, `.mbtn`).
- Routing: introduce `react-router-dom` (not yet a dependency in `apps/wellness`) with routes `/login`, `/signup`, `/link-member`, and `/` (Home, gated by `RequireAuth`).

## Error Handling

- **Login failure** (wrong password, unknown email): Supabase returns a generic `Invalid login credentials` error for both cases already — surfaced verbatim as "Incorrect email or password."
- **Signup, duplicate email:** Supabase's `signUp` returns a user object with no error but an empty `identities` array when the email already exists (its documented anti-enumeration behavior with email confirmation off, this is a real Supabase behavior to detect explicitly) → app checks for this and shows "An account already exists for this email — sign in instead," linking to `/login`.
- **Invite code, invalid/expired:** `redeem_invite_code` raises `invalid_or_expired_code` → caught, distinct message: "That code is invalid or has expired — check with your coordinator."
- **Invite code, already linked** (`on conflict do nothing` in the RPC): treated as success — redirect to Home rather than erroring, since the end state (user linked to member) is already satisfied.
- No rate limiting / lockout on invite-code attempts for V1 — codes are coordinator-issued and not a public signup surface, so brute-force risk is low relative to the added complexity.

## Testing

- **pgTAP** (`supabase/tests/database/rls.test.sql`, extending the existing 6-assertion suite): `member_links` select policy (owner reads own links, non-linked user denied, coordinator reads all); `redeem_invite_code` happy path (creates link, marks invite used); redeem with expired code (raises exception); redeem with already-used code (raises exception, since `used_at is null` fails the lookup).
- **Vitest** (`apps/wellness`): `AuthProvider` reducer/state-transition tests using a mocked Supabase client — no session → session with 0 links → session with 1 link (routes to Home, `is_self` preferred) → session with 2 links (switcher visible). Login/Signup/LinkMember components get a rendering + submit-happy-path test each using React Testing Library, consistent with the existing `App.test.tsx` pattern.

## Out of Scope (this spec)

- Admin-side invite-code generation UI (codes are SQL/script-generated by the developer for V1).
- Password reset flow (deferred — flag as a fast-follow before real user onboarding begins, since email+password with no reset path is a support burden).
- Phone/OTP auth (may revisit later per V1_SCOPE's original "email or phone OTP" framing, not needed for V1 per this session's decision).
- Tiered permissions between linked accounts on the same member (all linked accounts currently have equal access).
